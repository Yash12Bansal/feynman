# 06 — Board Intelligence & Latency

## Problem Statement

Two critical problems block the product from feeling magical:

1. **Latency**: `draw_design_diagram` takes 5-15s (Claude generates full DiagramSpec from scratch). Real-time teaching needs visuals in <2s.
2. **Board intelligence**: The LLM generates diagrams in isolation. It can't reference, modify, or build on existing visuals. The board is a display, not a teaching tool.

**These are connected**: board awareness enables incremental updates (faster) instead of regenerating from scratch.

## Existing Infrastructure (What We're Building On)

- `LessonPlan` with `visual_suggestions` per `ConceptNode` — anticipation data exists
- `SceneGraph` — pixel-precise spatial model (frontend reports bounds, spatial relationships, density, free regions)
- `BoardState` + `BoardManager` — element tracking, multi-board with push/pop mirroring doubt branches
- Fast visual tools: `show_equation` (instant), `draw_scene` with 33 components (~1s), `draw_diagram` (fast), `show_graph` (fast)
- Board manipulation: `highlight`, `annotate`, `highlight_walk`, `clear_board`
- Board summary already in LLM prompt via `BoardState.summary()` → `SceneGraph.summary()`
- **`data_pre_compute/` pipeline** — PDF-to-curriculum pipeline producing `ConceptGraph` with typed relationships, exhaustive node summaries, teaching order, and pre-extracted textbook images

## Curriculum Data: Two Sources

The anticipation engine can draw from **two curriculum sources** with very different richness levels:

### Source A: Runtime LessonPlan (current)
- Generated by Claude at session start from topic name
- `ConceptNode` has: title, description, key_points, `visual_suggestions` (free text)
- Visual suggestions are generic: "draw free body diagram", "show equation"
- No content depth — the LLM invents the structure from a topic name

### Source B: Pre-computed ConceptGraph (from `data_pre_compute/`)
- Built offline from actual textbook PDFs
- `ConceptNode` has: **exhaustive summary** (teacher can deliver full lecture from it alone), page ranges, hierarchy
- `ConceptEdge` has: typed relationships — `prerequisite`, `leads_to`, `related`, `example_of`, `parent_child`
- `get_teaching_order()` gives pre-computed DFS sequence
- Pre-extracted textbook images linked by page range

**ConceptGraph is dramatically better for anticipation.** Instead of "draw free body diagram" (generic), we get the actual concept content describing exactly what the diagram should show, what forces to include, what angle, what labels. This produces much better pre-generated diagrams.

### Integration strategy

When a ConceptGraph is available for the session's topic:
1. **Derive LessonPlan from ConceptGraph** — map graph nodes to LessonPlan ConceptNodes, preserving teaching order
2. **Use node summaries as visual generation prompts** — richer than `visual_suggestions`
3. **Use relationship edges for board intelligence** — prerequisite edges inform what to keep visible, leads_to edges suggest visual transitions
4. **Reference pre-extracted images** — textbook diagrams available by page range

When no ConceptGraph exists:
- Fall back to runtime `generate_lesson_plan()` (current behavior)
- Anticipation uses `visual_suggestions` (less rich but functional)

```python
    node_id: str
    topic_name: str
    summary: str          # EXHAUSTIVE — teacher can lecture from this alone

    target_id: str

class ConceptGraph:
    chapter_title: str
    nodes: dict[str, ConceptNode]
    edges: list[ConceptEdge]
    get_teaching_order() -> list[ConceptNode]  # DFS in book order

    get_related_edges(node_id) -> list[ConceptEdge]
```

## Phase 1: Anticipation Engine

**Goal**: Pre-generate design diagrams before they're needed so they're instant when the teaching agent requests them.

**Impact**: 0ms for on-plan design diagrams (90%+ of lesson). This is the biggest single latency win.

### 1.1 Create `anticipation.py`

New file: `backend/src/feynman/agent/anticipation.py`

```python
class AnticipationEngine:
    """Pre-generates design diagram specs from curriculum data.
    
    Supports two curriculum sources:
    - ConceptGraph (from data_pre_compute): richer prompts from exhaustive node summaries
    - LessonPlan: fallback using visual_suggestions
    """
    
    # Cache: (concept_index, suggestion_index) -> DiagramSpec dict
    _cache: dict[tuple[int, int], dict]
    
    # Store the prompt text used for each cached spec (for matching)
    _prompts: dict[tuple[int, int], str]
    
    # Track in-flight generations to avoid duplicates
    _generating: set[tuple[int, int]]
    
    async def warm_from_graph(self, graph: ConceptGraph, plan: LessonPlan,
                               start: int = 0, count: int = 3):
        """Pre-generate using ConceptGraph node summaries (preferred path).
        
        For each concept in range:
        - Use node summary to build a rich, specific diagram prompt
        - Include relationship context (what's prerequisite, what follows)
        - Reference page ranges (for potential textbook image retrieval)
        
        The prompt for a concept like "Free Body Diagrams" becomes:
          "Draw a free body diagram. Context: [exhaustive summary describing
           exactly what forces, what setup, what labels, from the textbook]"
        vs the LessonPlan path which would just say:
          "Draw a free body diagram"
        """
        
    async def warm_from_plan(self, plan: LessonPlan, start: int = 0, count: int = 3):
        """Pre-generate using LessonPlan visual_suggestions (fallback path).
        
        For each concept in range, for each visual_suggestion:
        - Classify: does this need design agent? (skip equations, graphs, scenes)
        - If yes: build prompt from concept title + description + key_points + suggestion
        """
    
    async def warm(self, plan: LessonPlan, start: int = 0, count: int = 3,
                   graph: ConceptGraph | None = None):
        """Unified entry point — routes to graph or plan path."""
        if graph:
            await self.warm_from_graph(graph, plan, start, count)
        else:
            await self.warm_from_plan(plan, start, count)
        
    def match(self, prompt: str, concept_index: int) -> dict | None:
        """Find a cached spec matching the agent's draw_design_diagram prompt.
        
        Strategy: check concept_index's cached suggestions. Score each by keyword
        overlap (tokenize both, compute Jaccard similarity). If best score > 0.3,
        return that spec.
        
        Also checks concept_index ± 1 as secondary search — the agent might
        reference a visual slightly before/after the concept boundary.
        """
        
    async def _generate_one(self, key: tuple[int, int], prompt: str):
        """Generate a single design diagram spec and cache it.
        
        Uses the same design_bridge path as draw_design_diagram.
        Logs timing for latency analysis.
        """
```

### 1.2 ConceptGraph → visual prompt extraction

The key function that makes graph-sourced anticipation better:

```python
def _build_prompt_from_graph_node(self, node: ConceptNode, 
                                    graph: ConceptGraph) -> str | None:
    """Extract a design diagram prompt from a graph node's summary.
    
    Returns None if the node doesn't need a design diagram
    (e.g., purely algebraic concept with no visual component).
    
    The prompt includes:
    - What to draw (extracted from summary — diagrams, setups, apparatus)
    - Context from the summary (what labels, what relationships to show)
    - Prerequisite context from edges (what students already understand)
    
    Example output for a node about "Young's Double Slit":
      "Draw a double-slit experiment setup showing: a monochromatic light source
       on the left, a barrier with two narrow slits separated by distance d,
       and a screen on the right showing an interference pattern. Label the
       path length difference (d sin θ), the central maximum, and the first
       few bright and dark fringes. Show the wave paths from both slits
       converging at a point on the screen."
    
    vs LessonPlan visual_suggestion: "draw double slit experiment diagram"
    """
```

**Classification heuristic** (`_needs_design_agent`): keywords like "diagram", "draw", "illustrat", "show setup", "apparatus", "figure", "schematic" → design agent. Keywords like "equation", "formula", "graph", "plot", "chart", "derive", "prove" → skip (fast tools handle these). When source is ConceptGraph, also check if node summary describes any physical setup or spatial arrangement.

**Matching strategy**: When `draw_design_diagram(prompt=...)` is called during concept N, check all cached suggestions for concept N. Score by keyword overlap (Jaccard). Also check N±1 as secondary. Threshold > 0.3 for match.

### 1.3 ConceptGraph → LessonPlan conversion

New file or function in `backend/src/feynman/agent/lesson_plan.py`:

```python
def lesson_plan_from_graph(graph: ConceptGraph, 
                            grade_level: str = "") -> LessonPlan:
    """Derive a LessonPlan from a pre-computed ConceptGraph.
    
    Maps graph teaching order → LessonPlan concept sequence.
    Uses node summaries to generate visual_suggestions (more specific
    than runtime LLM generation because we have the actual content).
    
    Only includes top-level and first-level nodes — deeper sub-topics
    are folded into their parent's key_points.
    """
    teaching_order = graph.get_teaching_order()
    concepts = []
    for node in teaching_order:
        if node.level > 1:
            continue  # fold into parent
        concepts.append(ConceptNode(
            title=node.topic_name,
            description=node.summary[:200],  # truncated for LessonPlan format
            key_points=_extract_key_points(node),
            visual_suggestions=_extract_visual_suggestions(node, graph),
            estimated_minutes=_estimate_time(node),
        ))
    return LessonPlan(
        topic=graph.chapter_title,
        objective=f"Teach {graph.chapter_title}",
        concepts=concepts,
        grade_level=grade_level,
    )
```

```python
@function_tool()
async def modify_design_diagram(
    ctx: RunContext, 
    target_id: str, 
    modification: str,
    zone: str = "",
    timing: str = "visual_first",
) -> str:
    """Modify an existing design diagram without regenerating from scratch.
    
    Much faster than drawing a new diagram. Use when you need to:
    - Change a parameter (angle, force magnitude, position)
    - Add/remove elements from an existing diagram
    - Change colors or labels
    - Adapt a diagram for a follow-up explanation
    
    Args:
        target_id: Element ID of the design diagram to modify (e.g., "design-1").
        modification: What to change. Be specific.
            Examples: "Change the incline angle to 45 degrees"
                      "Add a friction force vector pointing down the slope"
                      "Remove the normal force and highlight gravity only"
                      "Change all labels to use SI units"
    """
    tc: TeachingContext = ctx.userdata
    existing_spec = tc.board_manager.active_board.state.get_design_spec(target_id)
    if not existing_spec:
        return f"No design diagram found with ID {target_id}. Use draw_design_diagram instead."
    
    modified_spec = await modify_design_diagram_spec(existing_spec, modification)
    
    instruction = DrawDesignDiagramInstruction(
        title=modified_spec.get("title", ""),
        description=modification,
        spec=modified_spec,
        zone=_parse_zone(zone),
        sync_mode=_parse_timing(timing),
    )
    instruction.element_id = target_id  # Same ID = in-place update on frontend
    await _publish_visual(ctx, instruction)
    
    # Update stored spec
    tc.board_manager.active_board.state.store_design_spec(target_id, modified_spec)
    
    return f"Modified {target_id}: {modification}"
```

### 2.4 Board context: WHERE it actually lives

**Clarification**: The design agent generates self-contained SVG diagrams on its own canvas
(900x650). It doesn't position things on the board — the zone system handles that. So passing
the full board state (SceneGraph positions, spatial relationships) to the design agent is
**wrong** — that data is irrelevant to a self-contained diagram.

**Board intelligence lives in the TEACHING AGENT, not the design agent.**

The teaching agent already gets board state in every prompt (`_build_board_state_section()`).
It sees what's on the board and decides:
- Call `draw_design_diagram` with a specific prompt (new diagram)
- Call `modify_design_diagram` with the existing spec (modification — THIS is board context)
- Call `highlight_walk` / `annotate` (reference existing content)
- Call `switch_board` (navigate to earlier board)

The teaching agent's PROMPT to the design agent is the right channel for context.
No need to pass raw board state to the design agent separately.

**Exception — the modify path**: `modify_design_diagram` (2.2) passes the existing DiagramSpec
to Claude. This IS board context — the most useful kind: "here's exactly what exists, change X."

**Deferred**: If we later find that design diagrams look inconsistent with each other
(clashing color schemes, label styles), we can add a lightweight style hint:
```python
# Only if needed — not in initial implementation
style_hint = extract_style_from_spec(existing_design_specs)  # colors, fonts, stroke widths
```
But this is polish, not architecture.

## Phase 3: Board Intelligence — "Where and What, Seamlessly"

**Goal**: Make the board feel like a master teacher's whiteboard — right things in logically right places, spatial narrative that students can "read", consistent patterns.

**The core gap**: The infrastructure exists (zones, SceneGraph, board state tracking) but the teaching agent has almost no spatial reasoning guidance. Current zone instructions are 5 generic bullet points. The agent picks zones ad-hoc.

**The solution has four layers:**

### 3A: Teaching Scenario Templates (highest impact — prompt engineering)

A teacher doesn't think "which zone is free?" They think "I'm explaining a concept with a diagram and equation" — and that PATTERN dictates the layout.

```
### Tool Routing Rules (CRITICAL — prevents bad text rendering):

The design agent renders text as bare SVG `<text>` elements with no font styling — this 
looks bad. Text that can be shown as HTML should NEVER go through the design agent.

```
STRICT TOOL ROUTING:
- Text (definitions, key points, titles, explanations) → show_text (clean HTML, Inter font)
- Equations (any math, formulas, expressions) → show_equation (KaTeX, beautiful)
- Step-by-step algebra/derivations → step_equation (KaTeX steps with annotations)
- Data visualization (plots, charts) → show_graph (Chart.js)
- Abstract relationships (flowcharts, concept maps) → draw_diagram (node/edge)
- Physical/scientific diagrams with spatial precision → draw_design_diagram (SVG)
- Simple science setups (forces, optics, circuits) → draw_scene (component library)

NEVER use draw_design_diagram to display:
- Definitions or explanations (use show_text)
- Standalone equations (use show_equation)  
- Lists or bullet points (use show_text)
- Anything that is primarily TEXT — the design agent renders text badly

draw_design_diagram is ONLY for spatial visual content: apparatus, constructions,
annotated illustrations, diagrams where element POSITIONS matter.
```

Text that is PART of a diagram (axis labels, force labels, component names) stays
as svg_text within the design agent — but this is addressed separately in Phase 4
(font styling fix for design agent frontend).

### Spatial Rules (ALWAYS apply):
1. Related things go ADJACENT — equation next to its diagram, not across the board.
2. Temporal flow goes TOP→BOTTOM — first things at top, later things below.
3. One main visual anchor per board — don't compete for center attention.
4. Use annotate(action="arrow") to visually connect related elements across zones.
5. Clear old content before reusing a zone — never overlap.
6. If the board has >5 elements, clear non-essential ones before adding more.
```

### 3B: Board Relationship Graph (semantic graph of element relationships)

Right now board elements are independent entries in a flat dict. No relationship types,
no clusters, no way to reason about "these 4 elements form one logical unit."

A board graph with typed edges gives us: cluster detection, grouped summaries for the LLM,
lifecycle management (clear a cluster), modification propagation, and spatial rule enforcement.
Mirrors the ConceptGraph pattern — graphs for curriculum, graphs for the board.

**Two complementary graph layers per board:**
- `SceneGraph` (exists): SPATIAL — "design-1 is left_of eq-2" (from frontend bounds)
- `BoardGraph` (new): SEMANTIC — "eq-2 illustrates design-1" (from agent declarations)

#### New file: `backend/src/feynman/agent/board_graph.py`

```python
class BoardRelation(StrEnum):
    """Semantic relationship types between board elements."""
    ILLUSTRATES = "illustrates"      # equation/text describes a diagram
    DERIVES_FROM = "derives_from"    # next step in a derivation chain
    COMPARES_WITH = "compares_with"  # parallel comparison
    SUPPORTS = "supports"            # supporting detail for a main visual
    ANNOTATES = "annotates"          # annotation/highlight (ephemeral)

class BoardEdge(BaseModel):
    source_id: str
    target_id: str
    relation: BoardRelation
    label: str = ""

class BoardGraph:
    """Semantic relationship graph of board elements.
    
    Complements SceneGraph (spatial) with pedagogical relationships.
    Enables: cluster detection, grouped summaries, lifecycle management.
    """
    _edges: list[BoardEdge]
    
    def add_edge(self, source_id: str, target_id: str, 
                 relation: BoardRelation, label: str = ""):
        """Declare a semantic relationship between two elements."""
    
    def remove_element(self, element_id: str):
        """Remove all edges involving this element."""
    
    def clear(self):
        """Remove all edges."""
    
    def get_edges(self, element_id: str) -> list[BoardEdge]:
        """All edges involving this element."""
    
    def get_cluster(self, element_id: str) -> set[str]:
        """All elements transitively connected to this one (BFS).
        Returns the full connected component."""
    
    def get_clusters(self, element_ids: set[str]) -> list[set[str]]:
        """All connected components on the board.
        Each cluster is a group of semantically related elements."""
    
    def get_anchor(self, cluster: set[str], 
                   board_elements: dict) -> str | None:
        """Find the 'anchor' of a cluster — the main visual others support.
        Heuristic: element with most incoming edges, or first diagram/scene type."""
    
    def summary(self, board_elements: dict, scene_graph: SceneGraph) -> str:
        """Clustered summary merging semantic relationships with spatial data.
        
        Output format:
          Cluster: Free Body Analysis [anchor: design-1]
            design-1 (Free body diagram) — center-left, large
              ├── eq-2 (F = ma) ──illustrates── center-right
              ├── step-1 (Resolve forces) ──derives_from eq-2── bottom-center
              └── text-1 (Key insight) ──supports── top-center
          
          Standalone:
            graph-1 (a vs F plot) — bottom-right
          
          Open regions: top-left, top-right, bottom-left
        """
```

**Relationship type → spatial rules** (enforced by layout templates in 3A):

| Relation | Spatial Rule | Why |
|----------|-------------|-----|
| `illustrates` | ADJACENT zone (left↔right) | Equation next to its diagram |
| `derives_from` | BELOW the source | Derivations flow downward |
| `compares_with` | PARALLEL position (left↔right halves) | Side-by-side comparison |
| `supports` | NEAR the target (same column) | Supporting detail stays close |
| `annotates` | Overlays target (ephemeral) | Like pointing at the board |

```python
    element_id: str
    type: str
    zone: BoardZone | None = None

class BoardState:
    _elements: dict[str, BoardElement]
    scene_graph: SceneGraph       # spatial (from frontend bounds)
    board_graph: BoardGraph       # semantic (from agent declarations) — NEW
    
    def summary(self) -> str:
        """Combined summary: clusters + spatial + open regions."""
        # Prefer clustered summary (board_graph + scene_graph)
        clustered = self.board_graph.summary(self._elements, self.scene_graph)
        if clustered:
            return clustered
        # Fallback: scene_graph spatial summary (no relationship data yet)

            return sg
        # Fallback: flat zone-based listing
        return self._flat_summary()
```

```python
def _build_graph_context(tc: TeachingContext) -> str:
    """When ConceptGraph is available, add relationship hints."""
    if not tc.concept_graph:
        return ""
    
    current_node = tc.current_graph_node
    if not current_node:
        return ""
    
    edges = tc.concept_graph.get_related_edges(current_node.node_id)
    hints = []
    for edge in edges:
        if edge.relation == RelationType.PREREQUISITE:
            # Find which board has visuals for the prerequisite concept
            hints.append(f"- Prerequisite: {edge.label} (check earlier boards)")
        elif edge.relation == RelationType.LEADS_TO:
            hints.append(f"- This leads to: {edge.label} (keep visuals for reference)")
        elif edge.relation == RelationType.EXAMPLE_OF:
            hints.append(f"- Example opportunity: {edge.label}")
    
    if hints:
        return "\n## Cross-concept connections\n" + "\n".join(hints)
    return ""
```

This helps the agent:
- Reference prerequisite visuals (switch_board to earlier board)
- Keep current visuals visible for upcoming concepts (don't clear too early)
- Draw connections between related concepts (annotate arrows across boards)

## Session Audit System (Cross-Cutting — Built Into Every Phase)

**Problem**: Almost every system has a graceful fallback that masks failure. Anticipation
cache miss falls back to real-time generation. Board graph with no edges falls back to
flat list. Layout template ignored falls back to ad-hoc zones. The lesson runs fine while
half the features are silently degraded. Without explicit observability, there's no way to
know what's actually working during a live local run.

**Solution**: A `SessionAudit` that tracks what each system ACTUALLY DID during a lesson.
Not just "did the lesson run" but "did each system contribute as designed." Built
incrementally — each phase adds its own audit events. The audit produces a structured
report that Yash can share for verification.

### File: `backend/src/feynman/agent/session_audit.py`

```python
class SessionAudit:
    """Tracks what each system actually did during a teaching session.
    
    Every system logs its decisions here — not just successes, but fallbacks,
    skips, and degradations. The summary report makes silent failures visible.
    
    Built incrementally: each phase adds its own event types.
    """
    
    def __init__(self):
        self._events: list[AuditEvent] = []
        self._warnings: list[str] = []
    
    def record(self, system: str, event: str, **details):
        """Record an event from a specific system.
        
        system: "anticipation", "tool_routing", "board_graph", "layout", 
                "concept_context", "modify", "doubt"
        event: what happened — "cache_hit", "cache_miss", "fallback", 
               "edge_declared", "cluster_formed", etc.
        details: key-value pairs with specifics
        """
    
    def warn(self, system: str, message: str):
        """Record a warning — something that works but shouldn't be happening."""
    
    def summary(self) -> str:
        """Generate the full audit report."""
```

### How It Gets Built (Per Phase)

Each phase adds its audit events. The SessionAudit class is created with Phase 1 and
grows as phases are implemented:

| Phase | Audit Events Added |
|-------|-------------------|
| 1 | `anticipation.pre_generated`, `anticipation.cache_hit`, `anticipation.cache_miss`, `anticipation.source` (graph vs plan) |
| 2 | `anticipation.graph_loaded`, `anticipation.prompt_quality` (enriched vs basic) |
| 3 | `modify.called`, `modify.time_ms`, `modify.regeneration_avoided` |
| 4 | `routing.tool_call` (which tool, what content type), `text_quality.svg_text_with_math` |
| 5 | `layout.pattern_used`, `layout.zone_assigned`, `layout.zone_missing` |
| 6 | `board_graph.edge_declared`, `board_graph.cluster_formed`, `board_graph.orphan_element`, `board_graph.equation_without_relation` |
| 7 | `concept_context.stamped`, `concept_context.missing`, `concept_context.graph_hint_shown` |
| 8 | `doubt.background_gen_fired`, `doubt.visual_ready_before_needed`, `doubt.fallback_to_scene` |
| 9 | (metrics aggregation, timing percentiles) |

### Integration Points

**In TeachingContext:**

**In each tool/system — example from anticipation cache check:**
```python
cached = tc.anticipation.match(prompt, tc.current_concept_index)
if cached:
    spec = cached
    tc.audit.record("anticipation", "cache_hit",
```

### Accessing the Audit

**Option 1 — Log dump on session end:**
```python

```

**Option 2 — API endpoint for live checking:**
```python
@router.get("/api/sessions/{session_id}/audit")
async def get_audit(session_id: str):
    return {"audit": tc.audit.summary()}
```

**Option 3 — Periodic log (every concept advance):**
```python
# In advance_concept()
logger.info("session_audit.checkpoint", 
            concept=tc.current_concept_index,
            report=tc.audit.summary())
```

Recommend Option 3 for local development — you see the audit grow after each concept,
not just at the end. If something breaks at concept 3, you see it immediately.

### Warning Severity Levels

```python
class AuditSeverity(StrEnum):
    INFO = "info"          # System working as designed
    DEGRADED = "degraded"  # Fallback active — feature not contributing
    WARNING = "warning"    # Unexpected behavior — should investigate
    CRITICAL = "critical"  # System broken — lesson quality affected
```

Examples:
- `INFO`: "anticipation.cache_hit" — working as designed
- `DEGRADED`: "anticipation.cache_miss for on-plan concept" — fallback to real-time gen, 
  matching may be broken
- `WARNING`: "equation without relates_to" — board graph incomplete, might be prompt issue
- `CRITICAL`: "anticipation engine failed to initialize" — no pre-generation happening

### How We Use This

After each phase implementation:
1. Yash runs a local teaching session
2. Shares the audit report (logs or API output)
3. I verify:
   - Are the new phase's events showing up? (feature is active)
   - Are there unexpected warnings/degraded events? (silent failures)
   - Are previous phases still showing healthy events? (no regression)
4. If issues found → fix before moving to next phase

This is our feedback loop. The audit is what makes "run it locally and check" actually
meaningful instead of "it seemed to work."
